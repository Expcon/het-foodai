# OvenCapture recognition-first presentation

The user's detailed UI and acceptance specification is the authority. Baseline is verified v1.2.2, commit c7d7e62. This work does not change model weights, preprocessing, inference parsing, capture worker, camera compatibility, metadata or anti-overwrite rules. No camera, serial or heating hardware is opened during acceptance.

Approach: keep Tkinter/ttk and ModelEngine. Add a presentation shell and a small request/result session object; retain the existing DesktopApp as owner of camera/model workers and settings. Rebuilding in a different GUI framework would add dependencies and duplicate validated behavior. Merely restyling the old sidebar would leave result association and imported-image flow unresolved. The chosen layout follows the user's four explicit areas, rather than introducing a new workflow.

Recognition is the default tab. Header shows app/version, selected loaded model, source and textual readiness. The image occupies the larger left area with aspect-preserving rendering. The right area shows the contract label, three model scores, measured preprocessing/inference/output-validation time, model identity/source/time and a thumbnail of the actual inference frame. Main action recognizes the selected source; secondary actions save the image or the complete result plus its frame. Empty and error states remain visible with logs collapsed.

Capture retains the numbered photo, burst, video, output path and metadata controls. Model management retains v2/R1/R2 catalog, manual ONNX/JSON/mode entry, real validation and batch-folder prediction. Advanced settings contains backend/format/resolution/driver and the existing optional serial monitor. No generic model-loader redesign is included; no such local branch was found during inventory.

Each prediction carries request ID, source generation, exact frame SHA and model generation/identity. Source changes clear results even while a worker is outstanding; a stale completion is rejected and must not clear a newer job. Camera live frames may continue, but a displayed result always keeps its exact inference thumbnail and timestamp. Disconnect clears camera results; imported-image results do not depend on camera connectivity. Manual model configuration edits invalidate readiness/results; delayed loads are accepted only for their original config. Repeated submit is refused while busy. Errors never retain a previous success card.

Result persistence writes only to an explicitly selected output directory, using exclusive new names. JSON binds the saved decoded frame SHA, original-file SHA when available, model and classes hashes, checkpoint identity, source/time, scores and measured timing scope. It makes no ground-truth, accuracy, calibrated-probability or unknown-class claim.

Visual choices made here: restrained light slate/white surfaces, dark text, one blue primary button, text plus status symbols, Microsoft YaHei UI, compact consistent spacing. No dashboard cards, gradients or generated mock screenshots. New independent version is v1.3.0-presentation-experimental.

Acceptance: real old/new v2/R1/R2 file predictions must match; source/async state tests, corruption/model errors, numbering/settings regression, whole-project tests, actual packaged EXE clicks and file recognition. Save actual runtime screenshots of not-ready, model-ready, result, error. Test window client areas 1366x768 and 1920x1080; distinguish real Windows DPI from Tk font-scale simulations and untested physical displays. Preserve old delivery hashes. All models/raw images/build outputs stay ignored.
